# 项目总览与短编号、短名称修复设计

## 方案选择

采用“汇总层工程量兜底 + 可安全执行的数据修复命令”。

其他方案未采用：只补中央账本记录会因 55 个项目缺少可确认的合同客户而被迫虚构业务维度；只在 Razor 页面临时求和会让项目列表、财务总览、提醒和导出继续互相矛盾。推荐方案把统一口径放在 `FinanceLedgerService`，同时只为资料完整的记录保留既有自动入账能力。

## 数据流与汇总口径

当前数据流为：

`合同工程量 -> FinanceSettlement(ProjectQuantity) -> FinanceLedgerService -> ProjectWorkspaceService -> 项目详情页`

历史导入缺失中间的 `FinanceSettlement`，因此修复后的汇总流程为：

1. 正常读取活动的外部中央账本结算并计算应收/应付。
2. 单独取得项目范围内所有活动 `ProjectQuantity` 来源 ID，防止筛选条件造成重复兜底。
3. 在没有截止日期的当前查询中，读取活动合同的工程量明细；仅对没有活动工程量结算的明细加入兜底应收。
4. 兜底金额为 `Quantity * UnitPrice`，应开金额仅统计 `RequiresInvoice=true` 的明细；正负兜底金额先在项目当前筛选范围内合并，再与已入账应收统一重算，避免负数扣减行被计算器逐行截断为零。
5. 合同、合作单位筛选直接使用合同维度；公司筛选使用与 `FinancePostingService` 一致的“合同公司分配优先、项目主公司其次”规则。
6. 再合并直接项目收付款和发票。直接销项发票除增加已开外，还必须冲减未开。

该算法不会创建不存在的合作单位或结算记录，因而所有 150 个受影响项目都能正确显示；资料完整的项目仍可通过现有入账服务生成正式中央账本记录。

## 页面显示

- 顶部经营条补齐应收、已收、未收、应开、已开、未开、应付、已付、未付。
- “金额进度”同时显示三组金额和比例，比例分母为工程量应收、需开票工程量和应付。
- `ProjectDisplayText` 统一负责未知日期、支付方式和历史发票方向值的中文标签；旧记录把 `Output` / `Input` 写入发票类型字段时，也分别显示“销项发票”/“进项发票”，Razor 页面不直接输出原始枚举字符串。
- 项目工程量、收款、发票和付款表格使用高于全局 `.table-wrap > table td` 的选择器优先级覆盖 `white-space: nowrap`，使用单元格内换行与 `overflow-wrap:anywhere`；日期和金额列保持不换行。各表保留合理最小宽度并通过横向滚动查看，避免名称跨列覆盖。
- 项目动态在服务层把审计动作键映射为中文；未知动作显示“系统操作”，页面不直接输出内部英文动作值。

## 短编号修复

新增 `LegacyDataRepairService`，只处理已知旧资料自动前缀：

| 实体 | 新格式 | 唯一范围 |
| --- | --- | --- |
| 项目 | `XM0001` | 全局 |
| 合同 | `XM0001-C01` | 项目内 |
| 工程量 | `QD001` | 合同内 |
| 员工 | `YG0001` | 全局 |
| 合作单位 | `HZ0001` | 全局 |
| 发票 | `FP000001` | 全局生成，满足公司+方向唯一约束 |
| 签约公司 | `GS0001` | 全局 |

服务识别旧资料 `OLD-*` 编号以及 8 个已确认由导入流程生成的 `OFFICIAL-*` 公司编码，先根据稳定排序生成碰撞安全映射，再在一个数据库事务中把目标编号改为唯一临时值并保存，最后写入正式短编号。任一步失败都会回滚。实体 GUID、外键、金额、日期和业务状态不变。返回结果包含每一条旧编号/新编号映射和各实体计数。

## 自动占位名称修复

旧资料导入曾把项目名或旧编号拼进展示名称，导致合同和工程量表格被长文本挤压。修复命令同时识别这些明确的自动占位模式，只改展示字段，不改用户真实业务名称：

| 实体 | 旧自动名称模式 | 新名称 |
| --- | --- | --- |
| 合同 | `{项目名}-原始主合同（待确认）` | `主合同（待确认）` |
| 工程量 | `待补工程量-{旧编号}` | 同一合同内 `待确认工程量1/2/3...` |
| 合作单位 | `待确认合作单位（旧资料补导）` | `待确认合作单位` |
| 合作单位 | 付款原文补建，且带“从旧资料原始合作单位补建”标记，不区分原名称长短 | `待确认单位0001`（序号取最终 `HZ` 编号） |
| 签约公司 | `待确认签约公司（旧资料补导）` | `待确认签约公司` |
| 财务账户 | `待确认账户（旧资料补导）` | `待确认账户` |

来源编号和人工核实说明继续保留在导入报告、备注或修复映射中，不再进入主要展示名称。官方 Python 转换脚本在工程量源名称为空时直接生成简短的 `待确认工程量N`。

合作单位修复会在首次处理后追加“系统已复核自动合作单位”标记；若旧版本已经把名称改成与当前 `HZ` 编号对应的“待确认单位+序号”，新版本只补标记，不重复覆盖名称。带标记的记录视为人工复核边界，后续重跑不再改名。

正常新建项目时，自动创建的主合同名称固定为“主合同”，避免再次把完整项目名称复制到合同名称中。

## 后续新建与复制编号

Web 层使用 `ShortBusinessNumber` 从现有编号中寻找第一个可用的标准短编号。项目建议值查询包含停用项目，员工和合作单位建议值同样覆盖全部档案，避免页面给出已占用编号。项目、员工、合作单位和施工班组的新建或复制入口分别建议 `XMdddd`、`YGdddd`、`HZdddd`，不再将 `-COPY` 追加到源编号。复制名称统一使用紧凑中文“（副本）”；公司和设备仍要求用户填写新的唯一编码，但复制名称也不再使用带空格的“ - 副本”。保存时既有唯一性校验继续作为并发兜底。

## 员工工作簿结构行过滤

原始员工工作簿的个人明细页在“姓名”列下方还会出现“已付款”分区标题，空白模板页同时保留一行数值为 0 的占位明细。旧解析器把标题当参与人、把 0 当有效数据行，组合后生成了没有任何业务关联的伪员工。修复在源头执行两层过滤：参与人读取跳过已知分区标题；应付和已付同时为 0 的明细不进入分析结果。非零明细若找不到真实参与人则返回导入错误，不再创建结构标签员工。

Web 启动程序增加一次性命令 `--repair-legacy-project-data`：先调用 SQL Server 备份执行器创建 `.bak`，再运行修复并把 JSON 映射报告写入 `App_Data/logs`。命令输出备份、报告路径和变更计数，便于自动审计。第二次执行只产生零变更报告。

## 兼容与回滚

- 不增加数据库字段或迁移。
- 外部 Excel 若仍引用旧编号，可通过映射报告替换；系统内部关系不依赖业务编号。
- 回滚方式为停止服务并恢复命令执行前生成的 SQL Server 完整备份。
- 汇总兜底是只读计算，回滚代码即可恢复旧行为。

## 验证策略

- SQLite 单元测试覆盖“有工程量无结算”“部分已入账防重复”“直接收款/发票冲减余额”“截止日期不倒灌”。
- SQLite 数据修复测试覆盖格式、碰撞、外键保持和幂等。
- Python 测试覆盖旧项目转换脚本生成 `XM0001` 和简短工程量占位名称。
- 静态 Web 测试覆盖中文日期/支付方式和表格换行规则。
- Web 测试覆盖历史 `Output` / `Input` 中文回退、标准短编号建议和所有复制入口不再出现 `-COPY`。
- SQL Server 修复前后审计覆盖实体数量、旧前缀、自动长名称、唯一键、截图项目金额和全项目汇总。
- 启动服务后用真实项目详情页复核金额、比例和表格显示。

## 2026-08-02 新增设计：全系统列表统一排序

### 方案

采用“分页主列表服务端排序 + 已完整加载小列表客户端排序”的混合方案。

- 项目、员工、经营台账和中央账本等分页列表由 PageModel/服务接收 `SortKey`、`SortDescending`，在 `Skip/Take` 前排序。
- 已完整渲染的 DataWorkbench 列表在共享工具栏中显示排序菜单，并在浏览器内对全部已加载行排序。
- 未接入 DataWorkbench 的详情页、弹窗和小表由共享 `list-sorting.js` 自动识别可见 `.data-table`，动态插入紧凑排序菜单。
- 图表辅助表、空表、单行表和显式 `data-list-sort-disabled` 的表不增强；合计行、空状态行和 `data-sort-fixed` 行固定在末尾。

全部改为服务端排序会要求为 70 余张小表增加独立查询契约，改动与维护成本过高；全部改为浏览器排序又无法保证分页第一页拿到全局最新数据。混合方案能同时满足准确性与全覆盖。

### 共享契约

`DataWorkbenchViewModel` 增加排序选项、默认排序键、默认方向和是否服务端排序。`_DataWorkbench.cshtml` 统一渲染“排序”选择器，项目与员工传入服务端模式，其余工作台使用客户端模式。

共享 JavaScript 使用以下规则：

1. `Intl.Collator("zh-CN", { numeric: true })` 比较 `XM0227`、`YG0096` 等短业务编号。
2. 去除千分位、货币符号和百分号后比较金额和比例。
3. 识别 `yyyy-MM-dd`、`yyyy/MM/dd` 与带时间的常见页面日期；空值和“日期待确认”始终排在有效值之后。
4. 排序保持稳定；值相同时沿用原始顺序。
5. 使用 `localStorage` 以“路径 + 表格标识”为键保存小列表选择；服务端列表写入 `sortKey`、`sortDescending` 并清除页码参数。
6. 使用 `MutationObserver` 处理弹窗打开后才填充的名册和使用历史表。

### 默认规则

- 主档：业务编号自然降序，例如项目 `ProjectNumber DESC`、员工 `EmployeeNumber DESC`。
- 交易/记录：业务日期降序，再按业务 ID 或原始稳定顺序降序。
- 页面显式提供排序键时优先；否则按表头日期/时间、编号/编码顺序推断。
- 没有可判断“最新”的列时，服务端原始顺序作为“最新在前”，用户仍可按任一业务列排序。
- 工程量等固定语义列表保留“原业务顺序”，但首次进入仍按用户要求显示最新优先。

### 兼容性

- 不新增数据库字段或迁移。
- 不改变实体 ID、业务数据和表单字段名。
- 服务器端排序参数沿用现有 `SortKey` / `SortDescending`，修复 `_DataWorkbench` 中旧的 `sort` / `descending` 参数名不一致问题。
- 保存视图继续存储实际排序键和方向；旧视图没有排序键时回退到本页最新优先默认值。

### 测试

- Web 静态测试覆盖共享菜单、脚本加载、所有表格自动增强契约和分页 PageModel 的排序参数。
- PageModel/服务测试覆盖项目编号、员工编号和中央账本业务日期的降序及排序后分页。
- 浏览器验证项目首条 `XM0227`、排序菜单切换、刷新保持、详情小表独立排序、控制台无错误。

## 2026-08-03 新增设计：从备注安全回填项目日期

### 数据流

`Project.Notes` → `ProjectNoteDateParser` → 逐项目回填计划 → 备份/事务 → `Project.ActualStartDate` / `Project.ActualCompletionDate` → JSON 报告与 `AuditLog`

解析器只接受带完整年份的日期格式，并保留日期原文与邻近文本。候选日期必须在机器/设备/租赁上下文，或紧邻进场、退场、完工等生命周期词；付款、转账、发票、税金、保证金和工资上下文会被排除。开始候选按日期取最小值，结束候选按日期取最大值。只有开始事件而没有结束事件的项目只补开始日期。

回填服务先加载完整项目集合生成逐项目计划，再校验已有日期和日期顺序。已有日期不覆盖；候选完工早于已有/候选开工时只报告待核实，不写入。存在变更时开启单事务，更新并发戳和更新时间，写一条包含完整映射的系统审计日志后提交；无变更不写审计。

### 运维入口与回滚

新增精确维护参数 `--backfill-project-dates-from-notes`，与现有维护模式互斥。`Program` 在执行服务前创建 SQL Server `.bak`，完成后把备份路径、报告路径、逐项目状态和计数写入 `App_Data/logs`。回滚使用命令输出的备份恢复，不修改数据库结构。

### 风险控制

- 不用无年份日期推断年份。
- 不把备注中付款/发票日期当项目完工日期。
- 对日期倒置、格式异常和只含进场的项目保留待核实原因。
- 只写空字段，保证重复执行幂等。
