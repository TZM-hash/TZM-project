# 根因与数据库审计（2026-08-01）

## 数据链根因

- `FinanceLedgerService.BuildProjectSummariesAsync` 只累计活动的 `FinanceSettlements`。
- 项目工程量明细位于 `ContractLineItems`，项目详情中的工程量列表可直接读取这些记录。
- 历史资料导入后，737 条工程量中有 331 条没有活动的 `ProjectQuantity` 应收，影响 150 个项目，缺失应收合计 `157,262,884.732`。
- 99 个项目完全没有应收结算；其中 44 个资料完整可自动同步，55 个合同缺少可确认的合作单位，不能安全生成中央账本记录。
- 所有受影响项目都有签约公司，因此项目级汇总可以使用工程量兜底，但不能虚构合同客户。
- 直接项目收款和发票已被汇总服务识别；当前直接发票只增加已开，没有冲减未开。

## 页面显示根因

- `Details.cshtml` 直接输出 `DateOnly` 和支付方式字符串，因此未知日期显示为 `0001/1/1`，枚举字符串显示为英文。
- 全局 `.data-table td` 使用 `white-space: nowrap`；项目财务表又使用固定布局和窄列，长合同编号与单位名称会越过单元格。

## 自动占位名称补充审计

- 第一轮全库审计发现 227 个合同名为“项目名-原始主合同（待确认）”，17 个空工程量名称被写成“待补工程量-旧长编号”，另有 1 个占位合作单位和 1 个占位签约公司带“（旧资料补导）”。
- 对所有字符串型 `Name` / `Number` / `Code` / `Title` 字段执行动态模式审计后，又发现 1 个财务账户名“待确认账户（旧资料补导）”。
- 最终短名称采用“主合同（待确认）”“待确认工程量N”“待确认合作单位”“待确认签约公司”“待确认账户”；技术来源信息保留在修复 JSON 映射和备注中。
- 项目 `XM0007` 修复后合同名为“主合同（待确认）”，四条工程量依次为“待确认工程量1/2/3”和真实名称“钢筋损耗”。

## 二次全库与实页审计补充

- 付款明细页抽查发现，183 个合作单位带“从旧资料原始合作单位补建”标记，其中 76 个名称超过 20 字，典型值把业务说明、姓名、身份证号、银行卡号和银行名称整段拼入主名称。
- 这些记录的业务编号已经缩短为 `HZ0001` 格式，但名称仍会撑宽下拉框；修复规则只处理带明确自动补建标记且名称过长或含连续 8 位以上数字的记录，统一改为 `待确认单位+HZ数字序号`，不修改没有来源标记的正式单位名称。
- 10 个活动项目同时存在已入账正数工程量和未入账负数扣减工程量。原实现逐条调用中央账本计算器，负数行被按零截断，导致应收高于工程量净额；修复后先合并正负兜底净额，再与已入账应收统一计算。
